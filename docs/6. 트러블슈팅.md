## Case 1: 마크다운 계층 구조 보존을 위한 AST 기반 할 일 정렬 알고리즘

### Problem (Situation & Cause)
옵시디언의 마크다운 할 일(Task) 목록은 들여쓰기(Indent)를 통해 부모-자식 관계를 형성합니다. 하지만 마감일(D-Day)을 기준으로 전체 텍스트 라인을 단순히 배열 정렬(`Array.sort`)하게 되면, 하위 서브 태스크들이 부모와 분리되어 엉뚱한 곳으로 흩어지면서 **문서의 논리적 계층 구조가 완전히 파괴되는 치명적인 문제**가 발생했습니다.

### Solution (Technical Approach)
텍스트를 평면적으로 다루는 것을 포기하고, 마크다운의 들여쓰기 깊이를 분석하여 텍스트를 **트리(Tree) 형태의 논리적 자료구조(AST)로 파싱(Parsing)하는 전용 엔진**을 구축했습니다. 부모 노드 내의 자식 배열 안에서만 재귀적(Recursive)으로 D-Day 정렬을 수행한 뒤, 최종적으로 다시 마크다운 평문으로 평탄화(Flatten)하는 알고리즘을 설계했습니다.

### Code Architecture (Implementation)

**[After] 텍스트를 AST 형태로 파싱 후 재귀적 정렬 수행**
```typescript
// TaskUtils.ts - 마크다운 텍스트를 트리 구조(TaskNode)로 파싱
parseTasksToTree(lines: string[]): TaskNode[] {
    const nodes: TaskNode[] = [];
    const stack: { indent: number, children: TaskNode[] }[] = [{ indent: -1, children: nodes }];

    lines.forEach(line => {
        const indent = line.trim() === "" ? 999 : (line.match(REGEX.INDENT) || [""])[0].length;
        // 메타데이터(마감일, 마커 등) 추출
        const metadata = { /*... 추출 로직 ...*/ };
        const node: TaskNode = { line, indent, metadata, children: [] };
        
        // 스택을 활용하여 현재 들여쓰기 레벨에 맞는 부모 노드를 찾아 자식으로 편입
        while (stack.length > 1 && stack[stack.length - 1].indent >= indent) stack.pop();
        stack[stack.length - 1].children.push(node);
        stack.push(node);
    });
    return nodes;
}

// 트리 구조 내에서만 뎁스별로 안전하게 정렬 (부모-자식 보존)
sortTaskTree(nodes: TaskNode[]) {
    nodes.sort((a, b) => {
        const pa = MARKER_PRI[a.metadata.marker.trim()] || 99;
        const pb = MARKER_PRI[b.metadata.marker.trim()] || 99;
        if (pa !== pb) return pa - pb; // 1. 마커 우선순위 정렬
        return a.metadata.date.localeCompare(b.metadata.date); // 2. 날짜 정렬
    });
    // 자식 노드가 있다면 재귀적으로 파고들며 정렬
    nodes.forEach(n => { if (n.children.length > 0) this.sortTaskTree(n.children); });
}
```

### Impact (Result)
- **자료구조의 실무적 응용**: DOM 조작이 불가능한 순수 텍스트 환경에서, 스택(Stack)과 재귀(Recursion)를 활용해 직접 AST 변환 및 평탄화 엔진을 구현함으로써 알고리즘 설계 역량을 증명했습니다.
- **데이터 무결성 100% 보장**: 깊이가 10단계 이상 중첩된 복잡한 할 일 목록이라도, 들여쓰기 뎁스가 절대 붕괴되지 않고 각자의 컨텍스트를 유지한 채 완벽하게 정렬되는 무결성을 확보했습니다.

## Case 2: 들여쓰기(Indent) 스코프 기반 상태 하향 전파 엔진 구축

### Problem (Situation & Cause)
사용자가 최상위 부모 할 일에만 마감일(`#D-3`)을 명시하거나 완료 처리(`[x]`)를 했을 때, 하위의 자식 태스크들은 명시적인 속성이 없어 시스템이 이를 개별적으로 인식하지 못했습니다. 일일이 모든 서브 태스크에 마커를 달게 하는 것은 사용성(UX) 측면에서 최악이었습니다.

### Solution (Technical Approach)
앞선 파싱 엔진의 아이디어를 응용하여, 라인을 위에서 아래로 스캔하며 **현재 태스크보다 깊은 Indent를 가진 후속 라인들을 논리적 자식으로 간주(Context Scope)**하는 하향 전파(Downward Propagation) 스캐너를 자체 개발했습니다. 이를 통해 부모의 상태값과 마커를 하위 노드의 메모리 속성으로 덮어씌웠습니다.

### Code Architecture (Implementation)

**[After] 스코프를 식별하여 상위 속성을 하위로 전파**
```typescript
// TaskUtils.ts - 상태 및 마커 하향 전파 로직
applyMarkersToLines(linesArray: string[], todayObj: Date): string[] {
    const lineInfos = linesArray.map(l => ({ /* 라인별 메타데이터 객체화 */ }));

    // Downward 날짜 마커 전파
    for (let i = 0; i < lineInfos.length; i++) {
        if (lineInfos[i].hasDate) { // 부모 노드가 날짜를 가진 경우
            const sourceMarker = lineInfos[i].ownMarker;
            for (let j = i + 1; j < lineInfos.length; j++) {
                // 부모의 Indent와 같거나 작아지면(스코프 밖으로 벗어나면) 전파 중단
                if (lineInfos[j].indent <= lineInfos[i].indent) break;
                
                // 자식 노드가 부모보다 우선순위가 낮다면 부모의 마커로 덮어쓰기
                const pSource = MARKER_PRI[sourceMarker] || 99;
                const pChild = MARKER_PRI[lineInfos[j].marker] || 99;
                if (pSource < pChild) lineInfos[j].marker = sourceMarker;
            }
        }
    }
    // (완료 상태 하향 전파 로직도 동일한 스코핑 메커니즘으로 구현)
    // ...
}
```

### Impact (Result)
- **UX 극대화 (Zero-Effort)**: 사용자는 최상위 프로젝트(Task) 하나만 컨트롤하면 하위 작업들의 진행 상태와 우선순위가 자동 동기화되므로, 플래닝에 소모되는 피로도를 획기적으로 낮췄습니다.
- **성능 최적화**: 매번 트리를 전체 재구성하지 않고, 1차원 배열을 순회하며 Two-pointer 형태의 스코프(Scope) 스캔 방식을 적용하여 O(N)에 가까운 속도로 상태 전파 렌더링을 최적화했습니다.

## Case 3: 블록 ID 정규표현식을 활용한 In-place 동기화 및 텍스트 붕괴 방지

### Problem (Situation & Cause)
메인 스케줄 노트와 개별 프로젝트 노트를 양방향 동기화할 때, 노트 전체 텍스트를 읽고 통째로 교체(Replace)하는 방식은 매우 위험했습니다. 사용자가 임의로 작성해둔 다른 메모 영역이나 서식이 정규식 치환에 휩쓸려 **데이터가 영구적으로 날아가는(Lost Update)** 참사가 발생할 수 있었습니다.

### Solution (Technical Approach)
옵시디언의 고유 기능인 '블록 캐시 ID(`^1a2b3c`)' 메커니즘을 역이용했습니다. 동기화가 필요한 할 일 뒤에 6자리 랜덤 해시 ID를 자동 발급/부착하고, `REGEX.EXTRACT_ID` 정규표현식을 통해 해당 ID를 가진 정확한 라인만 찾아내어 핀포인트로 스왑(In-place Swap)하는 정밀한 동기화 엔진을 구축했습니다.

### Code Architecture (Implementation)

**[After] 블록 ID를 앵커(Anchor)로 활용한 핀포인트 동기화**
```typescript
// Synchronizer.ts - 특정 ID 기반 In-place 업데이트 로직의 핵심부
const originalIds = new Set();
const execMap = new Map(); // 최신 실행 상태(체크 여부 등)를 담은 Map

originalPlanLines.forEach(line => {
    const pMatch = line.match(REGEX.TASK_LINE);
    if (pMatch) {
        // 1. 라인 끝에 붙은 ^캐시ID 추출
        let { text, id } = this.utils.extractIdAndText(pMatch[3]);
        
        if (id && execMap.has(id)) {
            // 2. 일치하는 ID가 있다면 원본 텍스트를 유지한 채 상태 괄호 [x] 만 최신으로 교체
            const updatedExecTask = execMap.get(id);
            const status = (updatedExecTask.line.match(REGEX.STATUS_MATCH))[1];
            newPlanLines.push(`${pMatch[1]} [${status}] ${text} ^${id}`);
        } else {
            // 3. 동기화 대상이 아니면 원본 라인 100% 훼손 없이 보존
            newPlanLines.push(line);
        }
    } else {
        newPlanLines.push(line);
    }
});
```

### Impact (Result)
- **데이터 안정성(Fault Tolerance)**: 노트 내부의 어떤 영역을 유저가 수정하더라도, 정밀하게 타겟팅된 `Task` 블록 이외의 영역은 1바이트도 건드리지 않는 완벽한 격리(Isolation) 업데이트를 달성했습니다.
- **정규식 파싱 역량**: 복잡하게 뒤섞인 텍스트 스트림 속에서, 태스크 마커, 본문, 그리고 후위의 캐시 ID만을 분리해 내는 고난도의 정규표현식(`REGEX.EXTRACT_ID`) 설계 능력을 입증했습니다.

## Case 4: 마크다운 문서 오염 및 파괴 방지를 위한 방어적 프로그래밍(Defensive Programming)

### Problem (Situation & Cause)
빠른 할 일 캡처(Quick Capture) 기능을 구현할 때, 대상 스케줄 노트의 특정 헤더(`#### 할 일`)를 찾지 못하면 단순히 파일 맨 밑바닥 끝부분에 텍스트를 욱여넣는(Append) 하드코딩된 Fallback 방식이 존재했습니다. 만약 유저가 실수로 대상 섹션을 지워버린 상태에서 캡처가 실행되면, 유저의 소중한 노트 템플릿 포맷 전체가 붕괴되고 데이터가 엉뚱한 곳에 적재될 위험이 컸습니다.

### Solution (Technical Approach)
데이터의 무결성과 노트 생태계 보호를 최우선으로 삼아, 대상 섹션을 완벽히 찾지 못한 경우 **파일 수정을 즉각 중단(Return)시키고 명시적인 에러 알림(Notice)을 띄우는 방어적 프로그래밍(Defensive Programming)** 구조로 재설계했습니다. 불확실한 상황에서의 강제 쓰기 연산을 원천 차단했습니다.

### Code Architecture (Implementation)

**[Before] 실패 시 무분별하게 Append 하는 위험한 로직**
```typescript
if (!sectionFound) {
    // ❌ 위험: 헤더가 없어도 파일 맨 끝에 무조건 욱여넣어 문서를 오염시킴
    content = content.trimEnd() + "\n\n" + newTaskLine;
}
```

**[After] 조건 미충족 시 즉각 프로세스 중단 및 피드백 강화**
```typescript
if (!sectionFound) {
    // ✅ 안전: 헤더 미발견 시 문서 수정을 즉시 포기하고 유저에게 알림
    new Notice("❌ 스케줄 노트에 [#### 할 일] 헤더를 찾을 수 없어 캡처가 취소되었습니다.");
    return; // File I/O 프로세스 즉각 종료
}
```

## Case 7: 플러그인 핫 리로드(Hot Reload) 시 메모리 캐싱 충돌(TypeError) 해결

### Code Architecture (Implementation)
```powershell

npm run build
New-Item -ItemType Directory -Force -Path "C:\Users\kim50\...\.obsidian\plugins\myworld-task-manager"
```

## Case 8: 타사 플러그인(Obsidian Tasks) 경고창 스팸(Spam) 현상 방어

### Problem (Situation & Cause)
옵시디언 생태계 내에서 널리 쓰이는 `obsidian-tasks-plugin`과 본 플러그인의 루틴 콜아웃(`> [!routine]`) 기능이 충돌하는 현상이 발생했습니다. 라이브 프리뷰 상태에서 루틴 체크박스를 클릭하면, Tasks 플러그인이 이를 제어할 수 없다는 에러 경고창(Notice)을 매번 띄우며 사용성을 심각하게 저해했습니다. 이를 막고자 CSS 스니펫으로 `.notice` 전체를 숨겼으나, 이로 인해 본 플러그인의 필수 시스템 알림까지 모두 가려지는 부작용이 발생했습니다.

### Solution (Technical Approach)
순수 CSS로는 팝업 텍스트 내용을 필터링할 수 없다는 한계를 인지하고, 플러그인 로드(`onload`) 시점에 문서 전체의 DOM 변화를 감지하는 `MutationObserver`를 도입했습니다. 타사 플러그인이 생성하는 `.notice` 요소의 `innerText`를 실시간으로 검사하여 특정 경고 문구("obsidian-tasks-plugin warning")가 포함된 경우에만 해당 노드를 즉시 은닉(`display: none`)하도록 처리했습니다.

### Code Architecture (Implementation)
```typescript
// main.ts - Tasks 플러그인 특정 경고창 차단 옵저버
const noticeObserver = new MutationObserver((mutations) => {
    mutations.forEach((mutation) => {
        mutation.addedNodes.forEach((node) => {
            if (node instanceof HTMLElement && node.classList.contains("notice")) {
                const text = node.innerText || "";
                if (text.includes("obsidian-tasks-plugin warning") && text.includes("inside a callout")) {
                    node.style.display = "none";
                }
            }
        });
    });
});
noticeObserver.observe(document.body, { childList: true, subtree: true });
this.register(() => noticeObserver.disconnect());
```

### Impact (Result)
- **DOM 제어 및 이벤트 감지**: 옵시디언 플랫폼이 제공하는 API의 한계를 넘어 브라우저 네이티브 DOM API(`MutationObserver`)를 활용해 문제를 해결함으로써, 프론트엔드 환경에 대한 높은 이해도를 증명했습니다.
- **플러그인 생태계 공존(Co-existence)**: 타사 플러그인과의 마찰(Conflict)을 영리하게 우회하면서도 본 플러그인의 필수 기능은 살려내는 핀포인트(Pin-point) 예외 처리 로직을 구현했습니다.

## Case 10: 하위 작업의 시급성을 고려한 상향 전파(Upward Propagation) 정렬 알고리즘

### Problem (Situation & Cause)
마감일(D-Day)에 따른 AST 기반 할 일 정렬을 구현했으나, 부모 작업 자체의 마감일만을 기준으로 정렬하는 한계가 발견되었습니다. 예를 들어, 부모 작업의 마감일이 `2026-06-09`이고, 하위 서브 작업의 마감일이 `2026-06-08`로 더 급박하더라도, 정렬 엔진이 부모의 `06-09` 정보만 읽고 전체 덩어리를 하단에 배치해버리는 문제가 발생했습니다.

### Solution (Technical Approach)
자식들의 일정 중 가장 급박한 일정과 마커(우선순위)를 찾아 부모의 정렬 기준으로 덮어씌우는 **'상향 전파(Upward Propagation)' 알고리즘**을 정렬 엔진에 추가로 도입했습니다. 기존의 상태 '하향 전파(Downward)'가 속성의 상속을 담당했다면, 이번 '상향 전파'는 트리 정렬 시의 가중치 산정을 담당합니다.

### Code Architecture (Implementation)
```typescript
// TaskUtils.ts - 재귀적으로 자식의 최고 우선순위를 도출하는 로직
calculateEffectivePriority(node: TaskNode): { marker: string, date: string } {
    let bestMarker = node.metadata.marker;
    let bestDate = node.metadata.date;
    let bestPri = MARKER_PRI[bestMarker.trim()] || 99;

    for (const child of node.children) {
        const childEff = this.calculateEffectivePriority(child);
        const childPri = MARKER_PRI[childEff.marker.trim()] || 99;

        if (childPri < bestPri) {
            bestPri = childPri;
            bestMarker = childEff.marker;
            bestDate = childEff.date;
        } else if (childPri === bestPri && childEff.date.localeCompare(bestDate) < 0) {
            bestDate = childEff.date;
        }
    }
    node.metadata.effectiveMarker = bestMarker;
    node.metadata.effectiveDate = bestDate;
    return { marker: bestMarker, date: bestDate };
}
```

### Impact (Result)
- **자료구조의 응용 심화 (AST 활용)**: AST 트리 파싱 로직에 Bottom-Up 방식의 재귀 순회를 추가함으로써, 부모 작업의 일정이 널널하더라도 내부 자식 작업 중 단 하나라도 긴급한 것이 있다면 덩어리 전체를 최상단으로 끌어올리는 완벽한 계층형 정렬 시스템을 완성했습니다.

## Case 11: 전역 객체(Window) 확장을 통한 'any' 타입 캐스팅 제거 및 모듈 호환성 문제 해결

### Problem (Situation & Cause)
옵시디언 환경 내장 라이브러리인 `moment.js`를 호출할 때, 타입스크립트가 전역 `window` 객체에 `moment`가 존재하는지 알지 못해 `const now = (window as any).moment();` 형태로 불안전한 우회(Type Assertion)를 사용했습니다. 이는 엄격한 린트 환경에서 'Unexpected any' 에러를 유발했습니다. 또한 이를 고치기 위해 무작정 외부 패키지 `import { Moment } from "moment"`를 가져오면, 이번에는 "옵시디언 내장 패키지를 사용하라"는 스캐너 경고(Restricted Import)가 발생했습니다.

### Solution (Technical Approach)
타입스크립트의 **선언 병합(Declaration Merging)** 기능을 활용하여 근본적인 해결책을 마련했습니다. 외부 패키지가 아닌 옵시디언이 제공하는 자체 내장 모듈(`import { moment } from "obsidian"`)의 타입을 획득한 뒤, 전역 `Window` 인터페이스를 확장(`declare global`)하여 `moment` 프로퍼티의 존재를 타입 시스템에 공식적으로 등록했습니다.

### Code Architecture (Implementation)
**[Before] 임시방편적인 any 캐스팅 사용**
```typescript
// ❌ 컴파일러를 속이는 임시방편 (ESLint 경고 발생)
const now = (window as any).moment();
```

## Case 15: 읽기 모드(Reading View) 스케줄 Todo 글씨 클릭 시 체크박스 오작동 토글 방지

### Problem (Situation & Cause)
스케줄 노트의 `# Todo` 영역에 작성된 할 일 항목을 읽기 모드(Reading View)에서 조회할 때, 체크박스가 아닌 **글씨(텍스트)를 클릭하거나 드래그하여 선택하려고만 해도 체크박스가 제멋대로 토글(`[ ]` ↔ `[x]`)되고 자동 동기화가 실행되는 심각한 사용성 문제**가 발생했습니다.
원인을 분석해보니, 읽기 모드용 `MarkdownPostProcessor`에서 모든 `.task-list-item` 요소에 `capture: true`로 클릭 리스너를 바인딩하고 있었으며, 이벤트가 수신되자마자 즉시 `e.preventDefault()`와 `stopPropagation()`을 호출한 뒤 대상이 루틴 콜아웃 내부인지 체크박스(INPUT)인지 여부를 구분하지 않고 무조건 텍스트 매칭을 통해 마커를 반전시키고 있었습니다.

### Solution (Technical Approach)
라이브 프리뷰와 마찬가지로 읽기 모드에서도 **루틴 콜아웃 내부가 아닌 일반 태스크에서는 오직 `<input type="checkbox">` 엘리먼트를 직접 클릭했을 때만 토글 로직을 수행**하도록 이벤트 필터링 방어 코드를 구현했습니다.
클릭 대상이 루틴 콜아웃 외부이면서 체크박스가 아닌 일반 텍스트/여백일 경우, 어떠한 이벤트 차단(`preventDefault`)도 수행하지 않고 즉시 반환(`return`)하여 옵시디언 고유의 텍스트 선택, 커서 위치 지정, 링크 클릭 등 기본 사용자 인터랙션이 100% 정상 작동하도록 보장했습니다.

### Code Architecture (Implementation)
**[Before] 클릭 타깃을 구분하지 않고 무조건 이벤트를 차단하며 토글 실행**
```typescript
// main.ts (읽기 모드 포스트 프로세서)
const handler = (e: Event) => {
    e.preventDefault(); // ❌ 글씨 클릭 시에도 기본 동작(텍스트 선택) 차단
    e.stopPropagation();
    // 타깃이 체크박스인지 확인하지 않고 무조건 파일 텍스트 매칭 후 토글 수행
};
```

**[After] 클릭 타깃이 체크박스 또는 루틴 내부일 때만 선별적 이벤트 가로채기**
```typescript
// main.ts (읽기 모드 포스트 프로세서)
const handler = (e: Event) => {
    const target = e.target as HTMLElement;
    if (!target) return;

    const isCheckbox = target.tagName === "INPUT" && (target as HTMLInputElement).type === "checkbox";
    const { cleanText, categoryName, itemIndexInCat, isInsideRoutineCallout } = extractTaskContextFromDOM(target);

    // ✅ 핵심 방어: 루틴 콜아웃 내부가 아닌 일반 태스크(스케줄 Todo 등)에서는 오직 체크박스 직접 클릭만 처리!
    if (!isInsideRoutineCallout && !isCheckbox) {
        return; // 글씨 클릭 시 기본 텍스트 선택 및 커서 진입 완벽 보장
    }

    e.preventDefault();
    e.stopPropagation();
    e.stopImmediatePropagation();
    // 이후 토글 및 파일 저장 수행
};
```

### Impact (Result)
- **자연스러운 텍스트 인터랙션 회복**: 스케줄 노트의 Todo 목록에서 본문 텍스트를 드래그하여 복사하거나 링크를 클릭할 때 체크박스가 뒤집히는 오작동이 100% 근절되었습니다.
- **루틴과 Todo의 명확한 역할 분리**: 전체 라인이 버튼처럼 동작해야 하는 루틴 단계(`> [!routine]`)와, 체크박스와 텍스트 선택이 독립적이어야 하는 일반 Todo 항목의 인터랙션 정책이 일관되고 정교하게 정립되었습니다.

## Case 16: DataviewJS 템플릿 리터럴 내 정규표현식 이스케이프 소실로 인한 날짜 클릭 불능 해결

할 일 목록에서 특정 작업을 "중요(Important)" 상태로 강조하는 기능을 기획할 때, 흔히 체크박스 마커를 `- [!]` 등으로 변형하는 방식을 고려하기 쉽습니다. 그러나 다음과 같은 치명적인 구조적 결함과 초기 구현 결함이 존재했습니다:
1. **상태 불일치 및 마커 소실(State Drift)**: 옵시디언 기본 코어 엔진은 `- [!]` 상태의 체크박스를 클릭하면 `- [x]`(완료)로 토글하지만, 다시 클릭하여 미완료로 되돌릴 때 원본 마커 `[!]`가 아닌 기본 `- [ ]`로 복구시켜 중요 상태가 영구 소실됩니다.
2. **기존 D-Day 마커 계산 엔진과의 충돌**: 플러그인은 이미 마감일에 따라 `[!]`(지연), `[0]`(오늘), `[1]`(내일) 등의 커스텀 마커를 연산하는 엔진을 내장하고 있어, 중요도 마커와 D-Day 마커 간의 주권 다툼(Race Condition)이 발생합니다.
3. **달력 팝업 요일 그리드 CSS 클래스 불일치 버그**: 렌더링 컨테이너(`.myworld-cal-dows`)와 개별 요일 셀(`.myworld-cal-dow`) 간의 CSS 클래스 선언 불일치로 인해, 요일 헤더가 가로 7열이 아닌 세로 7줄로 붕괴되는 심각한 UI 왜곡이 발생했습니다.
4. **달력 팝업 [중요] 버튼 저장 미호출 결함**: 달력 팝업 내 `[ 중요 ]` 버튼 클릭 시 내부 플래그만 토글되고 실제 파일 저장 콜백(`onSelect`)이 즉시 호출되지 않아, 사용자가 중요 버튼만 누르고 팝업을 닫았을 때 변경 사항이 저장되지 않고 무시되는 UX 결함이 발생했습니다.

### Solution (Technical Approach)
1. **체크박스 불변 원칙 (Checkbox Marker Invariance)**: 체크박스 마커는 옵시디언 표준인 `- [ ]`와 `- [x]`만을 100% 유지하여 기존 완료 토글 및 D-Day 엔진과의 충돌을 원천 차단했습니다.
2. **원문 식별자 보존 & 화면 완전 은닉 (Hidden Star Strategy)**: 마크다운 파일 원문에는 `⭐` 식별자를 텍스트로 보존하여 검색성과 데이터 영속성을 확보하되, 화면 렌더링 파이프라인(CodeMirror 6, Reading View, Dataviewjs)에서는 `.myworld-hidden-star { display: none !important; }`를 적용하여 `⭐` 텍스트를 완전히 은닉했습니다.
3. **체크박스 간섭 차단 및 [D] 디데이 뱃지 골드 네온 발광 (Option 1: Neon Glow)**:
   - 좌측에 선(`border-left`)을 그으면 옵시디언 기본 체크박스와 겹치거나 들여쓰기가 밀리는 구조적 한계를 극복하기 위해, 좌측 선을 과감히 배제했습니다.
   - 대신 중요 태스크의 디데이 가상 뱃지(`.dday-virtual-badge.is-important`)에 **골드 네온 빛남(`text-shadow: 0 0 6px #f59e0b, 0 0 12px rgba(245, 158, 11, 0.7)`)** 효과를 적용하여, 체크박스와의 겹침 0% 및 우아하고 시인성 높은 하이라이트를 완성했습니다.
4. **달력 팝업 슬림화 (235px) 및 1-Click 원자적 저장 플로우**:
   - `styles.css`의 요일 컨테이너(`.myworld-cal-dows`)에 `display: grid !important; grid-template-columns: repeat(7, 1fr) !important;`를 적용하여 요일 그리드를 완벽 복구하고, 가로 폭을 235px로 아담하고 슬림하게 컴팩트화했습니다.
   - `[ 중요 ]` 버튼 클릭 시 별(⭐) 이모지 없이 순수 텍스트 상태로 색상만 토글되며, 즉시 `onSelect(initialDate, currentImportant)`를 호출하고 팝업을 닫도록 개선하여 단 1클릭으로 파일 저장 및 빛남 효과가 즉시 발현되도록 인터랙션을 완성했습니다.

- **슬림 달력 팝업 & 논블로킹 인플레이스 토글**: 235px의 아담한 달력 팝업에서 `[ 중요 ]` 버튼을 눌러도 팝업이 꺼지지 않고 그 자리에서 활성화/비활성화 상태가 켜지며 실시간 저장되므로, 날짜 변경 작업과의 매끄러운 연속성을 완벽하게 보장합니다.

## 33. 완료된 할 일(- [x])의 취소선 이모지 깨짐 및 별(⭐)/날짜(📅) 노출 문제

### Problem
- 옵시디언에서 할 일을 완료(`- [x]`) 처리했을 때, 취소선(`text-decoration: line-through`)이 달력 이모지(`📅`) 한가운데를 가로지르면서 이모지가 깨져 보이고, 미완료 상태에서는 숨겨져 있던 중요도 별(`⭐`) 식별자가 취소선과 함께 훤히 노출되는 심각한 시각적 부자연스러움이 발생했습니다.
- 원인:
  1. Reading Mode 후처리기(`MarkdownPostProcessor`)에서 완료된 태스크(`data-task="x"`)를 감지하면 조기 반환(`return`)하여, 별(`⭐`)을 숨기는 `.myworld-hidden-star` 치환 로직이 동작하지 않았습니다.
  2. Live Preview 및 Dataview에서도 완료된 태스크의 날짜(`📅 YYYY-MM-DD`)를 별도로 은닉하지 않고 일반 텍스트 상태로 두어 취소선이 이모지를 관통했습니다.

### Solution
1. **완료된 할 일의 날짜/별 완전 은닉 원칙 확립**:
   - 이미 완료된 태스크는 마감 기한과 중요도 뱃지가 더 이상 필요하지 않으므로, 사용자의 명확한 선택에 따라 **완료된 항목에서는 별(`⭐`)과 날짜(`📅`)를 모두 화면에서 완전 은닉(`.myworld-hidden-completed-item { display: none !important; }`)** 처리했습니다.
2. **Reading Mode / Live Preview / Dataviewjs 전 영역 일괄 적용**:
   - **Reading Mode**: `taskEl.getAttribute("data-task") === "x"`인 경우 텍스트 노드를 순회하여 `⭐`, `[중요]`, `📅 YYYY-MM-DD`를 추출하고 `.myworld-hidden-completed-item` span으로 치환하여 화면에서 완전히 숨김.
   - **Live Preview (CodeMirror 6)**: `isCompletedTask`인 라인의 날짜 매칭 구간에 `Decoration.mark({ class: "myworld-hidden-completed-item" })`를 부여하여 화면에서 숨김.
   - **Dataviewjs (`scRender.js` & `TemplateHelper.ts`)**: `t.completed`가 참인 경우 D-Day 뱃지를 제거하고 날짜 및 별을 숨김 span으로 래핑.
3. **결과**: 완료 체크박스를 누르는 즉시 날짜와 별이 마법처럼 사라지고, 순수 할 일 본문 텍스트에만 단정하게 취소선이 그어져 완벽하게 심플하고 깔끔한 완료 UI를 구현했습니다. 체크를 해제하면 다시 날짜와 디데이 뱃지가 정상 노출됩니다.
